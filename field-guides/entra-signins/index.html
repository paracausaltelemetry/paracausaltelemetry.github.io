Visual reference for Microsoft Entra ID sign-in logs on cases: the four sign-in log types, the fields that matter, error codes and which "failures" are normal interrupts, Conditional Access results, tokens and sessions, and how adversary-in-the-middle phishing, token theft, device code phishing, password spray and MFA fatigue show up. Users, IPs and IDs below are placeholders. For what an attacker did after signing in, see the Microsoft 365 unified audit log field guide.

The mental model

Every token Entra issues is a sign-in event. A person typing a password is an interactive sign-in; an app quietly refreshing a token is non-interactive, and those are usually far more numerous. Apps signing in as themselves are service principal sign-ins.

LogSentinel tableHolds
Interactive user sign-insSigninLogsA user entered something: password, MFA, passkey
Non-interactive user sign-insAADNonInteractiveUserSignInLogsToken refreshes and SSO done by a client for the user
Service principal sign-insAADServicePrincipalSignInLogsApps signing in with their own secret or certificate
Managed identity sign-insAADManagedIdentitySignInLogsAzure resources signing in with a managed identity

How long they last

Read: export sign-in logs to Log Analytics, a storage account or a SIEM as soon as a tenant is onboarded. 30 days is often less than an incident needs. Sentinel's retention is whatever the workspace is set to; 90 days is included.

Read: a stream of "failures" from one user's own devices is usually interrupts (50074, 50140) and expired sessions. Filter those out before you count failures.

Conditional Access results

Policy resultMeans
successThe policy applied and its controls were met
failureThe policy applied and blocked the sign-in
notAppliedThe policy's conditions didn't match
notEnabledPolicy is off
reportOnlySuccess / reportOnlyFailure / reportOnlyNotApplied / reportOnlyInterruptedReport-only: what would have happened

Watch for: a successful sign-in where every policy shows notApplied. Either the app or location is excluded, or there's a gap the attacker found.

Tokens and sessions

TermMeans
Access tokenShort-lived (around 60 to 90 minutes). Revoking sessions doesn't kill ones already issued unless the app supports continuous access evaluation
Refresh tokenLong-lived, used to get new access tokens without the user. What token theft goes after
Primary refresh token (PRT)The device-level token on Entra-joined or registered Windows, macOS and mobile devices
Continuous access evaluation (CAE)Lets Exchange, SharePoint and Graph reject tokens soon after a revoke or a location change
Token protectionBinds sign-in tokens to the device, so a stolen one doesn't work elsewhere

Attacks and how they show up

Adversary-in-the-middle phishing

SignField
Successful MFA sign-in from a hosting provider or VPN ASNAutonomousSystemNumber, IPAddress
App is OfficeHome or similar web portal, user agent unusual for this userAppDisplayName, UserAgent
Same SessionId from two IPs or countries within minutesSessionId across interactive and non-interactive logs
A new MFA method or inbox rule shortly afterAuditLogs, unified audit log

Other patterns

AttackShows up as
Password spray50126 for many users from one IP or a small set of IPs, a few attempts each, often against legacy protocols
MFA fatigueMany 500121 for one user, then a 0
Device code phishingAuthenticationProtocol == "deviceCode" for a user who never uses it, often from an unusual IP
Legacy auth abuseClientAppUsed of IMAP4, POP3, Authenticated SMTP or Other clients: no MFA possible
Token replayNon-interactive sign-ins from a new IP, ASN or country with no interactive sign-in there
Consent phishing65001 / 90095, then "Consent to application." in AuditLogs
Service principal abuseAADServicePrincipalSignInLogs from new IPs, or a new credential on the app in AuditLogs

Containment

GoalHow
Throw the attacker outRevoke sessions (Revoke-MgUserSignInSession) and reset the password; with CAE, most services reject old tokens within minutes
Mark the account"Confirm user compromised" in Identity Protection, so risk policies act on it
Remove their footholdDelete MFA methods and devices they registered; remove app consents and inbox rules
Block the sourceNamed location for the IPs or ASN, with a block policy (expect them to move)
Stop it happening againPhishing-resistant MFA (passkeys, Windows Hello), token protection, block legacy auth and device code flow where not needed

Queries

Password spray (Sentinel)

kqlSigninLogs
| where TimeGenerated > ago(1d)
| where ResultType == "50126"
| summarize attempts = count(), users = dcount(UserPrincipalName), apps = make_set(AppDisplayName, 5) by IPAddress, AutonomousSystemNumber
| where users > 10
| sort by users desc

MFA fatigue: denials then success

kqlSigninLogs
| where TimeGenerated > ago(1d)
| summarize denials = countif(ResultType == "500121"), successes = countif(ResultType == "0"), firstDenial = minif(TimeGenerated, ResultType == "500121"), lastSuccess = maxif(TimeGenerated, ResultType == "0") by UserPrincipalName
| where denials >= 5 and successes > 0 and lastSuccess > firstDenial

One session, several IPs

kqlunion SigninLogs, AADNonInteractiveUserSignInLogs
| where TimeGenerated > ago(7d)
| where ResultType == "0" and isnotempty(SessionId)
| summarize ips = make_set(IPAddress, 10), countries = make_set(tostring(LocationDetails.countryOrRegion), 5), asns = dcount(AutonomousSystemNumber) by UserPrincipalName, SessionId
| where asns > 1

Device code sign-ins

kqlSigninLogs
| where TimeGenerated > ago(30d)
| where AuthenticationProtocol == "deviceCode"
| project TimeGenerated, UserPrincipalName, AppDisplayName, IPAddress, Location, ResultType, UserAgent

Legacy authentication

kqlSigninLogs
| where TimeGenerated > ago(7d)
| where ClientAppUsed in ("IMAP4", "POP3", "Authenticated SMTP", "Exchange ActiveSync", "Other clients", "MAPI Over HTTP", "Exchange Web Services")
| summarize attempts = count(), successes = countif(ResultType == "0") by UserPrincipalName, ClientAppUsed, IPAddress

Spray in SecOps

udmmetadata.event_type = "USER_LOGIN"
metadata.product_name = "Azure AD" nocase
security_result.action = "BLOCK"
$ip = principal.ip
match:
  $ip
outcome:
  $failures = count(metadata.id)
  $users = count_distinct(target.user.email_addresses)
order:
  $users desc

Tune: non-interactive sign-ins don't always reach SecOps or Splunk: check the feed includes them before concluding token replay didn't happen.
