Visual reference for Okta on cases: how sign-in and SSO work, what the policies and factors are, how to read the System Log, and what account takeover, MFA fatigue and session hijacking look like. Users, IPs and IDs below are placeholders.

The mental model

Okta is the front door. A user authenticates once to Okta (password plus factors, as policy demands), gets an Okta session, and Okta vouches for them to every app over SAML or OIDC.

Org
Your Okta tenant: acme.okta.com, plus an admin console at acme-admin.okta.com.
Okta session
Created at sign-in, held in a browser cookie. Steal the cookie and you skip the password and MFA.
Authenticator / factor
Okta Verify (push, number challenge, FastPass), FIDO2 / WebAuthn, phone, email, password.
FastPass
Passwordless, device-bound, phishing-resistant sign-in through Okta Verify.
Global session policy
Rules for creating the Okta session: which factors, how long it lasts.
Authentication policy
Per-app rules: who can reach the app, from where, with which assurance.
Network zone
Named IP ranges, ASNs or countries used in policies (allow, deny, "requires MFA").
ThreatInsight
Okta's IP reputation: flags or blocks credential-stuffing sources.
Super Administrator
Full control of the org. Treat every grant as an incident until proven otherwise.
API token
SSWS token acting as the admin who created it. Long-lived.

Where Okta sits

Read: compromise Okta and you reach every app below it. That's why admin roles, API tokens and factor changes are the events to watch.

Event record fields

FieldUse
eventTypeWhat happened
actor.alternateId / actor.typeWho did it: a user's login, or an app or API token
target[]Who or what it happened to (user, app, group, policy)
outcome.result / outcome.reasonSUCCESS, FAILURE, DENY, CHALLENGE, and why
client.ipAddress, client.userAgent.rawUserAgentWhere from, and what software
client.geographicalContextCity, country, coordinates

authenticationContext.externalSessionIdThe Okta session ID: pivot on it to follow one session

Read: externalSessionId is the most useful pivot. One session ID with two IPs, two ASNs or two user agents is session hijacking until proven otherwise.

Search syntax

texteventType eq "user.session.start" and outcome.result eq "FAILURE"
textactor.alternateId eq "j.smith@example.com" and client.ipAddress eq "203.0.113.45"
texteventType sw "user.mfa" and target.alternateId eq "j.smith@example.com"

Attack patterns

MFA fatigue

Read: many system.push.send_factor_verify_push events and deny_push, then a user.session.start SUCCESS from a new IP.

Session hijacking

Read: the stolen session's externalSessionId shows up from a new IP, ASN or user agent, often with no new user.session.start (no password or MFA needed).

Admin takeover

OrderEventMeans
1user.session.start from an unusual sourceAdmin account used
2user.mfa.factor.deactivate / .activateTheir factors swapped for the attacker's
3user.account.privilege.grantSuper Admin given to another account
4application.lifecycle.create (identity provider)Rogue IdP added for persistent access
5system.api_token.createAPI persistence

Containment

ActionHow
End every session for a userAdmin console › user › Clear user sessions, or DELETE /api/v1/users/{id}/sessions
Stop sign-insSuspend the user (keeps data, unlike deactivate)
Remove attacker factorsReset factors and re-enrol with the user in person
Kill an API tokenSecurity › API › Tokens › Revoke
Block a sourceNetwork zone with the IPs or ASN, plus a deny rule in policy
bashcurl -s -X DELETE "https://acme.okta.com/api/v1/users/00u1abcd2EFGHIJ3k4l5/sessions?oauthTokens=true" -H "Authorization: SSWS ${OKTA_API_TOKEN}"

Tune: oauthTokens=true also revokes the OAuth tokens issued to apps, so they stop working too.

Hunting in SecOps

MFA pushes per user

udmmetadata.log_type = "OKTA"
metadata.product_event_type = "system.push.send_factor_verify_push"
$user = target.user.email_addresses
match:
  $user
outcome:
  $pushes = count(metadata.id)
order:
  $pushes desc

Admin role grants

udmmetadata.log_type = "OKTA"
metadata.product_event_type = "user.account.privilege.grant"

Tune: user fields map differently per event type in the Okta parser. Check one event first.
